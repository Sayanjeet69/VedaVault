# VedaVault Retrieval

`vedavault_retrieval` owns the application's retrieval contracts. It does not
depend on LangChain or LlamaIndex.

## Evidence bundles

`Retriever` finds ranked evidence. `EvidenceBundle` transports that evidence
unchanged in a stable, model-independent form: verse identity, text layer,
score, source, and immutable metadata remain available for traceability. A
`GroundingContext` formats and constrains the bundle for model consumption
without adding interpretation. `AnswerContract` defines and validates the
answer shape: scriptural teaching, interpretation, and application are separate
fields. `LLMProvider` is the deliberately model-independent provider boundary;
Groq is the first concrete implementation. Scripture remains retrieved
evidence, while interpretation and modern application are not generated by
`EvidenceBundle` or `GroundingContext`.

## V1 hosted query and generation flow

The frozen V1 flow is:

    user query
    -> VedaVaultService
    -> LanguagePolicy
    -> QueryUnderstandingResult
    -> retrieval_query
    -> E5-small translations-only retrieval
    -> canonical best-hit verse deduplication
    -> EvidenceBundle
    -> GroundingContext
    -> GenerationRequest
    -> LLMProvider (GroqLLMProvider for V1)
    -> AnswerContract

QueryUnderstandingResult preserves the original user query exactly and keeps
the concise semantic retrieval query separate. The rewrite is used only for
search and is never scripture, retrieved evidence, or support for an answer.
An English rewrite is preferred for V1 because the trusted corpus has complete
English translations. This does not change response language: LanguagePolicy
still resolves an explicit response-language override first, then the
current-turn language, conversation language, and English fallback. The rewrite
provider can also report that clarification is materially required.

V1 first-class languages are English (en), Hindi (hi), Bengali (bn), and
Sanskrit (sa), including reasonable tolerance for Hinglish, Banglish,
Romanized Sanskrit, code switching, spelling mistakes, and informal input.
Tamil, Telugu, Marathi, and Gujarati remain in the model-independent enums for
future compatibility, but their product-quality validation is deferred to V2.

GroqQueryUnderstandingProvider and GroqLLMProvider share a small injectable
GroqClient. It uses the standard library HTTP client, reads credentials from
GROQ_API_KEY unless explicitly supplied by the host process, and defaults to
qwen/qwen3.6-27b, a 30-second timeout, temperature 0,
reasoning_effort="none", JSON output, and non-streaming requests. No key is
stored in source or artifacts. Grounded generation includes the existing
grounding rules, answer-contract rules, complete GroundingContext, resolved
language policy, answer mode, and exact supplied passage IDs. Parsed output is
constructed as the existing AnswerContract and passes existing evidence
validation.

Groq is one provider implementation, not a permanent architecture dependency.
Future Ollama, LM Studio, local, or other hosted implementations can implement
the same QueryUnderstandingProvider and LLMProvider boundaries.

`VedaVaultService` is the small provider-neutral composition layer. It sends
only the rewrite to `Retriever`, while `EvidenceBundle`, `GroundingContext`,
and `GenerationRequest` retain the original query. V1 orchestration requests
five canonical verses from translation-only retrieval, with best-hit
deduplication over 100 raw candidates. A clarification-required understanding
raises `ClarificationRequiredError` before retrieval or generation. The manual
`Scripts/vedavault_chat_smoke.py` entry point runs one explicitly invoked live
query; automated tests never invoke it.

## HTTP API

The API is a thin adapter over the frozen RAG V1 pipeline:

    VedaVaultService
           ↓
        HTTP API
           ↓
    future web frontend

`Backend/vedavault_api.py` exposes:

- `GET /health`: deterministic process health metadata. It does not construct
  the retrieval service or call Groq.
- `POST /answer`: validates a request, creates the existing `LanguagePolicy`,
  calls `VedaVaultService.answer(...)`, and returns compact frontend-safe JSON.

The answer request requires `query`. `input_language` defaults to `en`,
`response_language` defaults to the resolved input language, and `mode` defaults
to `textual`. Public V1 language codes are `en`, `hi`, `bn`, and `sa`. Answer
modes are `textual`, `philosophical`, and `application`.

The response contains the original query, retrieval rewrite, resolved response
language, mode, evidence sufficiency, scriptural teaching and citations,
interpretation, application, limitations, cited verse IDs, and ranked retrieved
verse IDs. It never returns prompts, raw provider messages, authorization data,
or the Groq API key.

Runtime configuration:

- `GROQ_API_KEY`: existing Groq credential read by `GroqClient`.
- `VEDAVAULT_INDEX_PATH`: optional override for the existing local index path.
- `VEDAVAULT_CORS_ORIGINS`: optional comma-separated allowed origins. Defaults
  to `http://localhost:3000,http://localhost:5173`; unrestricted `*` is refused.

The expensive local embedding provider and index are initialized lazily on the
first `/answer` request and cached once per API process. `/health` stays cheap.
Clarification requests return HTTP 409, identifiable upstream rate limits return
429, other provider failures return 502, unavailable local evidence/services
return 503, and unexpected failures return generic 500 JSON without internals.

Install the API runtime and offline test-client dependencies explicitly (the
repository does not install them automatically):

```powershell
python -m pip install -r Backend/requirements-api.txt
```

Launch locally from the repository root:

```powershell
python -m uvicorn vedavault_api:app --app-dir Backend --host 127.0.0.1 --port 8000
```

Example requests:

```text
GET http://127.0.0.1:8000/health
```

```powershell
$body = @{
    query = "gita me agar pura try karu fir bhi result na mile toh kya karu"
    input_language = "hi"
    response_language = "hi"
    mode = "application"
} | ConvertTo-Json

Invoke-RestMethod -Method Post `
    -Uri http://127.0.0.1:8000/answer `
    -ContentType application/json `
    -Body $body
```

The API adds no session state, persistence, authentication, streaming,
frontend, or deployment layer. RAG V1 remains unchanged underneath it.

## Multilingual retrieval benchmark

`Evaluation/bhagavad_gita_retrieval.json` is a deterministic, versioned
Bhagavad Gita retrieval benchmark with 50 curated questions. Its V1-core subset
covers English, Hindi, Bengali, and Sanskrit. The frozen benchmark also retains
Tamil, Telugu, Marathi, and Gujarati cases for deferred analysis, alongside
Romanized/transliterated input, code-switched queries, imperfect human input,
and explicitly marked cross-language retrieval cases.
Its controlled semantic categories include action and results, duty,
self/mortality, mind/meditation, desire/anger, grief/fear, knowledge,
devotion, liberation, and relationships/ethics.

Every item has stable metadata, primary verses, a narrow complete acceptable
verse set, and an evidence-oriented rationale. Primary verses are the strongest
targets; acceptable verses include every primary verse plus only defensible
alternatives. Tests validate every ground-truth canonical verse ID against the
local normalized corpus; retrieval output is not used to create ground truth.

The model-independent scorer preserves supplied ranks and reports Primary and
Acceptable Recall@5/@10, Acceptable Precision@5, Primary and Acceptable MRR,
duplicate-result rate by canonical verse identity, unique verses@10, and
chapter diversity@10. It can aggregate results—with subgroup sample counts—by
language, category, cross-language status, transliteration, code switching,
imperfect input, and difficulty tag. Duplicate indexed layers do not gain extra
relevance credit and remain visible as duplicates.

The evaluation workflow keeps raw retrieval metrics separate from an optional
verse-diversified downstream context. Recall, precision, MRR, duplicate rate,
and diversity diagnostics are computed from the original ranked candidates;
diversification reports only separately labeled context size/duplicate/diversity
diagnostics and never changes raw MRR ranks. Context size defaults to five,
while raw diagnostics default to ten ranked positions.

The benchmark defines what VedaVault intends to measure. It does not establish
that the current or any future embedding model performs well. Model selection
and execution against this benchmark are separate future work.

## Multilingual conversation policy

`LanguagePolicy` is immutable, model-independent language/conversation metadata
for a user turn and any already-known conversation context. It accompanies
`GenerationRequest`, not retrieval or grounding. Query understanding carries
the same policy while producing a separate search-only rewrite; the original
query remains the grounded generation query. The V1 flow is documented above.

Policy languages use stable ISO 639-1-style codes: English (`en`), Hindi
(`hi`), Bengali (`bn`), Sanskrit (`sa`), Tamil (`ta`), Telugu (`te`), Marathi
(`mr`), and Gujarati (`gu`). The first four are first-class V1 product targets.
The remaining language abstractions are retained for future expansion, with
product-quality validation deferred to V2. Unsupported policy values fail at
the validation boundary.

The policy can represent ordered current input-language hints, recent
conversation language, an explicit primary response-language request, an
optional distinct secondary language, code switching, transliteration/Romanized
input, a script hint, and a material clarification requirement. It contains no
query content. This layer does not perform language detection, spelling or
grammar correction, transliteration conversion, translation, query rewriting,
retrieval reranking, session persistence, or generation.

Primary response language resolves deterministically in this order: explicit
request, current-turn language hint, conversation language, then English. A
new current-turn hint therefore switches languages naturally; a short
follow-up may reuse conversation language. English is the fixed V1 fallback.
Secondary language represents a future concise alternate version, not a
duplicate answer.

Input language, writing script, transliteration, scripture/source language,
evidence language, conversation language, and response language are separate.
A Latin script hint is not proof of English; it can represent Romanized Hindi,
Bengali, or Sanskrit transliteration. Likewise, language policy never changes
the original scripture text, evidence language, canonical ID, metadata, or the
separation between scriptural teaching, interpretation, and application.

LanguagePolicy itself leaves ordinary imperfect human input unchanged,
including informal phrasing, abbreviations, misspellings, Romanized Indian
languages, and mixed queries. Query understanding performs the separate V1
retrieval rewrite. Clarification is represented only when ambiguity materially
changes retrieval or the answer.

This layer defines requirements and model-independent policy. V1 validation
covers English, Hindi, Bengali, Sanskrit, Romanized/transliterated input,
code-switching, imperfect input, response-language switching, citation fidelity,
and scripture/translation preservation. Broader language support still requires
separate V2 quality validation.

Install the optional local retrieval dependencies when building an index:

```powershell
python -m pip install -r Backend/requirements-retrieval.txt
```

## Embeddings

The default is `intfloat/multilingual-e5-small`, an MIT-licensed, Sentence
Transformers-compatible retrieval model. It is selected for the first local
index because VedaVault requires cross-language retrieval across Sanskrit,
Hindi, Latin transliteration, and English, while the prior MiniLM default was
English-oriented. Multilingual E5 supports the 100 XLM-R languages and its
model card instructs retrieval clients to prefix documents with `passage: ` and
queries with `query: `; the provider applies those prefixes automatically.
Those prefixes belong to the explicitly selected E5 prompt profile, not to the
Sentence Transformers adapter universally. When selecting another model with
`VEDAVAULT_EMBEDDING_MODEL`, set `VEDAVAULT_EMBEDDING_PROMPT_PROFILE=none`
for a model that requires no role prefix (or pass a custom profile when using
the provider in code), and rebuild the index.

The model produces 384-dimensional vectors, has 12 layers and 0.1B parameters.
The published `model.safetensors` file is about 471 MB. Plan for roughly 1-2 GB
of available RAM for a CPU Python process after framework/model overhead; the
resulting dense index is approximately 4 bytes x dimensions x document count.
Sanskrit is a low-resource language in the underlying multilingual coverage,
so this default is a practical starting point, not a quality guarantee. Evaluate
retrieval against a VedaVault Sanskrit/Hindi benchmark before treating it as a
production choice.

Alternatives considered:

| Model | License / dimensions | Local tradeoff |
| --- | --- | --- |
| `intfloat/multilingual-e5-base` | MIT, 768 | Higher-capacity XLM-R model, but its published weight file is about 1.11 GB and CPU/RAM cost is materially higher. Use when evaluation justifies it. |
| `BAAI/bge-m3` | MIT, 1024 | 8,192-token, multilingual dense/sparse/ColBERT model. It is substantially heavier and its extra retrieval modes are not used by this simple dense index. |
| `sentence-transformers/LaBSE` | Apache-2.0, 768 | Supports 109 languages and is strong for translated-pair matching, but Sentence Transformers documents it as weaker for general semantic similarity than translation matching. |

Set `VEDAVAULT_EMBEDDING_MODEL` to select a compatible model and
`VEDAVAULT_EMBEDDING_DEVICE` to choose a device. For CPU use, the provider
defaults to batches of 32 inputs and uses up to eight PyTorch threads (or the
available CPU count if lower). Sentence Transformers performs batching in one
`encode` call, allowing it to group similar-length inputs and avoid Python-level
setup for every small batch. Exact duplicate document texts are encoded once;
every document and its distinct metadata remain in the index.
Override them with `VEDAVAULT_EMBEDDING_BATCH_SIZE` and
`VEDAVAULT_EMBEDDING_CPU_THREADS`; lower either value on constrained machines.
The model's native sequence limit remains in effect by default. Set
`VEDAVAULT_EMBEDDING_MAX_SEQ_LENGTH` only for a deliberately evaluated local
development profile (for example, `256`); it trades context for speed and must
match when rebuilding and querying an index.
Changing a model or embedding configuration requires rebuilding the local index.
Each local index persists a versioned `index_manifest.json` with its model,
vector dimension, prompt profile/prefixes, normalization setting, and sequence
length. Loading it with an incompatible provider fails before retrieval rather
than silently mixing vector semantics.

Build the first local index and run the demo from the repository root:

```powershell
python Scripts/build_bhagavad_gita_index.py
python Scripts/retrieval_demo.py
```

The index is a local NumPy `.npz` file plus JSON document metadata. It can be
replaced later without changing document, chunking, filtering, or retrieval
interfaces.
